# The method

## The idea in one paragraph

Ordinary speculative decoding drafts **one target token per draft-model step**, and
reaches further ahead by running that draft model autoregressively — EAGLE-3 takes
seven steps to build a depth-7 tree. It also needs a draft model that shares the
target's vocabulary. This drafts a **whole phrase as one unit**.
A small head reads the target's last hidden state and produces a distribution over its
own vocabulary, whose entries are 1–3 word strings rather than tokens. The top-N
entries are expanded back into target tokens, merged into a prefix tree, and verified
in **one** target forward pass. Because the drafting vocabulary is independent of the
target's, the two never need to agree on tokenisation — which is the point, and the
reason the same construction applies across tokenizers.

## The four pieces

### 1. The vocabulary — words and phrases, not tokens

Built from a distilled corpus of the target's own outputs (~50,000 completions of maths
problems, generated by Qwen3-4B itself). Each completion is split into words by a
regex, and the split is **checked by reconstruction**: if re-joining the words does not
reproduce the text exactly, the completion is rejected. 43,550 of 49,997 survive.

Entries are then the most frequent 1-, 2- and 3-word sequences, capped at
`MAX_VOCAB = 80,000`:

| | count | share |
|---|---|---|
| 1 word | 36,358 | 45.4% |
| 2 words | 14,539 | 18.2% |
| 3 words | 29,103 | 36.4% |

Occurrence-weighted, one entry expands to **2.462 target tokens** and spans **2.33
words**. Boundary coverage is **1.000** — every word boundary in the corpus has some
entry that starts there.

**Why phrases are not redundant with BPE.** Qwen's 151,936-entry tokenizer and
Gemma-3's 262,145 contain **zero** multi-word tokens between them. Byte-level BPE and
SentencePiece both merge strictly *within* a word, because the pre-tokenizer splits on
whitespace first. Measured `words/token` is 0.72 for English maths on Qwen against
**2.33 words per drafted unit** here. The phrase layer is adding something the
tokenizer structurally cannot.

### 2. SLEM — expanding an entry back to target tokens

An entry is a *string*, so drafting it requires knowing which token sequence the target
would have produced for it. That is context-dependent in general. SLEM takes the modal
expansion: the tokenisation the target actually emitted most often for that string in
the corpus. It is right **90.3%** of the time.

The remaining 9.7% is a multiplicative loss on every draft, since landing is bounded by
`coverage × agreement`. Closing it by continuing BPE training with the whitespace
pre-tokenizer removed would make expansions exact by construction; that is not done
here.

### 3. The head — 21.9 M parameters

Two inputs: the target's last hidden state (2560-d) and the embedding of the last
emitted token. Output: a distribution over the 80,000 vocabulary entries. Parameter
count is `1,377,280 + V × 257`, so at V = 80,000 it is **21,937,792 — 0.545% of the
4.02 B target**.

Trained on 3,127,663 (hidden state, next-phrase) pairs extracted from the distilled
corpus, 24 epochs. Top-1 **0.394**, recall@8 **0.718**, recall@64 **0.865**.

Note what binds: the **vocabulary cap**, not the parameter budget. A 20 M ceiling would
allow V = 150,282. The head is this size because of a number that was chosen, not
found.

### 4. The verifier — N candidates in one pass, exactly

Each of the top-N entries expands to a token sequence. The sequences are merged into a
**prefix tree** and fed to the target in a single forward pass, with a 4-D attention
mask that lets each node attend only to its own ancestors and the real context. The
target's argmax at each node says which child, if any, continues; the walk follows the
deepest matching path, accepts it, and appends the target's own next token as a bonus.

Two properties make this exact:

- **A pass emits at least one token** — the bonus token is the target's own argmax, so
  `tok/pass ≥ 1.000` holds for any drafter however bad. This is asserted; a figure
  below 1 means tokens were generated and discarded, which is a measurement bug.
- **No two siblings in the tree carry the same token.** The prefix tree enforces this
  by construction. It matters because the walk resolves a match by position, so
  siblings sharing a token would make acceptance depend on candidate order — and 91.1%
  of the multi-word entries here have their first word as a standalone entry, so the
  collision is the common case, not an edge case.

The mask is asserted against a brute-force reference on random ragged batches at the
start of every run.

## What decides the speed

```
speedup ≈ tok_per_pass × (baseline pass cost / arm pass cost)
tok_per_pass = 1 + landing × accepted_tokens_per_landing
```

and the ceiling, before prediction quality enters at all:

```
tok_per_pass ≤ 1 + mean_expansion = 1 + 2.462 = 3.46
```

**That bound is the binding constraint on this configuration.** EAGLE-3 measures 3.811
tok/pass on GSM8K — above our ceiling — so no amount of better training closes that
particular gap while units cap at 3 words. Raising the unit length raises the bound;
everything else moves us toward it.

The second lever is **feed efficiency**, `(tok_per_pass − 1) / fed_tokens_per_pass`,
which is computable from anyone's published `(τ−1)/tree_size` and is how the headline,
the batching crossover and the depth decay all connect. Ours at N=8 is 0.114 against
EAGLE-3(60)'s 0.047 — we extract more per fed token at small feed — but EAGLE-3(16)
reaches 0.143, so this is not an argument that favours us at matched budget.

## Where it loses

- **Drafting quality, not cost.** Per verification pass on GSM8K our arm costs
  **79.0 ms against a 63.7 ms baseline (+24%)**, while EAGLE-3 costs **92.7 against
  59.6 (+56%)** — one head forward and a lookup against seven autoregressive draft
  forwards. Our pass is 15% cheaper, we feed fewer nodes (46 against 60), and we still
  lose because we bank 2.742 tokens in it against 3.811. The verifier and the draft are
  cheap; the guesses are worse.
- **Long answers.** Speedup falls with generation length. On MATH-500 we are level with
  EAGLE on the typical prompt and 12% behind across the whole workload, and the whole
  difference is the long answers — the set averages 571 tokens.
- **Out of domain.** 1.402× on MT-Bench against EAGLE's 2.005×. Boundary coverage is
  still 1.000 there, so it is not that the vocabulary lacks entries — the *phrases* are
  the wrong ones.
